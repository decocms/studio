O modo de voz substitui as mensagens e o composer do chat web por um orbe que fala.
Uma página adjacente ou o preview do site permanecem abertos. O agent selecionado, o
modelo, o contexto da página, as tools, as permissões e a fila de mensagens continuam
os mesmos para trabalho delegado. Uma conversa em tempo real, fornecida pela
ElevenLabs ou pela OpenAI, cuida da fala enquanto o agent selecionado do Studio
executa esse trabalho em segundo plano. Você pode continuar falando, perguntar sobre
o progresso ou enviar outro pedido enquanto uma tarefa de código está em execução.

Agents de código continuam executando o Claude Code no mesmo sandbox. O modo de voz
não muda o runtime fixado do chat, o checkout, o preview ou a sessão do Claude. O
estilo de resposta de voz acompanha cada turno porque o Claude Code restaura o
system prompt original ao retomar uma sessão. Turnos em texto restauram
explicitamente o estilo de resposta normal. Chats do Decopilot usam o mesmo
transporte de voz.

Escolha **Start voice mode** ao lado do composer e permita o acesso ao microfone.
**Back to chat** interrompe o microfone e a reprodução de áudio. Isso preserva o chat
e qualquer trabalho em execução. **Stop agent work** é um controle separado. Falar
enquanto uma resposta está tocando interrompe o áudio. Pedidos de trabalho completos
entram na fila normal do chat; pausas e saudações não iniciam turnos de código. Ambas
as companions respondem perguntas sobre o progresso dos pedidos desta chamada e das
tarefas criadas a partir do status de trabalho do Studio, sem iniciar um turno.
Aprovações, perguntas, erros e pedidos enfileirados permanecem visíveis no modo de
voz.

A companion confirma que o trabalho foi aceito sem alegar que já terminou. Quando o
agent do Studio termina, sua última parte em texto é enviada de volta para a
companion, que anuncia o resultado durante uma pausa silenciosa. Uma instrução por
turno pede ao agent em execução uma resposta curta e natural. Voltar para texto
restaura o estilo de resposta normal para as mensagens seguintes.

## Conversas da organização

O modo de voz também funciona com o Super Agent. Ele pode delegar perguntas sobre
serviços conectados, analytics e gerenciamento de tarefas pelas mesmas tools e
permissões do chat em texto. Por exemplo, peça para ele consultar analytics, iniciar
duas tarefas independentes e depois perguntar sobre o progresso delas enquanto
discute outro assunto. O Super Agent precisa ter acesso às integrações relevantes. O
GA4 pode responder perguntas de analytics; status de pedido ou fulfillment exige um
sistema de pedidos conectado.

O Studio mantém um status de trabalho para a chamada e o fornece como contexto para
a companion. Ele lista cada pedido falado como enfileirado, em execução, em execução
em segundo plano, ou finalizado, e cada task do board criada durante a chamada com
sua lane atual. Se o agent cria as tasks 1, 2 e 3 durante essa chamada, o navegador
as acompanha pelos eventos push existentes do task board e anuncia cada mudança de
lane. Outras tasks da organização permanecem silenciosas; uma pergunta sobre uma
delas é outro pedido para o Super Agent.

Pedidos em um mesmo chat são executados um turno por vez. Em turnos de voz, o agent
em execução recebe a instrução de iniciar pesquisa ou análise como uma `subtask` em
segundo plano, para que seu turno termine rápido e o próximo pedido falado não
precise esperar. A companion espera pelo turno de resultado dessa subtask antes de
anunciar a resposta; o turno que apenas a iniciou é reportado como trabalho em
segundo plano. Pedaços de trabalho separados que o usuário pede se tornam tasks do
board quando o agent tem tools de task board. Chats do Claude Code não têm a tool
`subtask`, então seus pedidos continuam na fila.

## Interface de conversa compartilhada

Os dois adaptadores de navegador implementam `publishUpdate`, controles de
microfone, volume e fechamento de sessão, e reportam pedidos através de
`onDelegate`. As atualizações distinguem contexto silencioso de anúncios falados e
podem carregar um ID de delegação. Isso permite que o Studio entregue o progresso ou
resultado de várias tasks de forma independente e fora de ordem. A OpenAI mapeia
isso para appends de thinking/commentary do Live; a ElevenLabs mapeia para
atualizações de contexto e mensagens de segundo plano explicitamente marcadas. Os
nomes de tools e esquemas de eventos de cada provider ficam dentro dos adaptadores.

O escopo da assinatura são as tasks criadas nessa chamada. O navegador lê os IDs
delas a partir dos resultados de `TASK_BOARD_ITEM_CREATE` nos turnos da chamada,
incluindo turnos de resultado em segundo plano, e filtra os eventos push do task
board para esse conjunto. Uma task não relacionada que termina em outro lugar
permanece silenciosa. O término de um turno de criação de tasks não estabelece que as
tasks criadas terminaram. Limitações conhecidas: reentrar no modo de voz começa com
um conjunto de tasks vazio, e uma mudança de lane durante uma reconexão do stream de
push só é reportada pela próxima mudança.

## Configuração de deployment

A seleção de provider é feita apenas no servidor, sem seletor de provider ou modelo
no produto. A ElevenLabs permanece o padrão. Defina estas variáveis em toda réplica
da API:

```bash
ELEVENLABS_API_KEY=<elevenlabs-api-key>
```

A chave precisa de acesso de leitura e escrita a ElevenAgents (`convai_read`,
`convai_write`), além de acesso a Text to Speech e Speech to Text para sessões de
navegadores mais antigos. Mantenha-a no servidor. O Studio cria um agent privado na
ElevenLabs para sua configuração de voz e o reutiliza entre sessões. Navegadores
recebem um token de conversa e um token de sessão assinado do Studio; eles nunca
recebem a chave de API.
O app web precisa de HTTPS para acesso ao microfone, exceto em localhost. Nenhum
callback de provider de entrada ou provisionamento manual de agent é necessário. As
réplicas da API precisam compartilhar o mesmo secret de autenticação do Studio e o
mesmo NATS.

Para tornar a OpenAI o padrão do deployment, configure:

```bash
VOICE_CONVERSATION_PROVIDER=openai
OPENAI_LIVE_API_KEY=<openai-api-key>
```

O adaptador da OpenAI usa o GPT-Live com delegação no cliente e WebRTC no
navegador. O Studio negocia a oferta SDP na sua API autenticada usando uma reserva
de sessão de uso único. O navegador recebe uma resposta SDP, não uma credencial da
OpenAI. Não é necessária uma chave da ElevenLabs. Mantenha a chave da ElevenLabs
durante um deployment contínuo se navegadores mais antigos ainda usarem os
endpoints de transcrição/síntese. A chave de longa duração da OpenAI permanece no
servidor da API. A seleção de provider nunca faz fallback silencioso para o outro
provider quando as credenciais estão ausentes.

Depois ative **Settings → General → Voice mode** para a organização. A flag de
organização `voice_mode` vem desativada por padrão. Ela é separada da autenticação:
somente o usuário dono pode iniciar uma sessão de voz para um chat hospedado e
gravável. Chats de terminal nativo e chats somente leitura não oferecem esse modo.

Variáveis opcionais:

| Variável | Padrão | Finalidade |
| --- | --- | --- |
| `VOICE_CONVERSATION_PROVIDER` | `elevenlabs` | `elevenlabs` ou `openai` |
| `OPENAI_LIVE_MODEL` | `gpt-live-1` | Modelo Live da OpenAI |
| `OPENAI_LIVE_VOICE` | `marin` | Voz Live da OpenAI |
| `ELEVENLABS_VOICE_MODEL` | `eleven_v4_turbo` | Modelo de síntese de fala |
| `ELEVENLABS_VOICE_ID` | `JBFqnCBsd6RMkjVDRZzb` | Voz da ElevenLabs |
| `ELEVENLABS_CONVERSATION_MODEL` | `gemini-2.5-flash` | ID do modelo de LLM de conversa suportado pela ElevenLabs |

As credenciais dos dois providers podem ser configuradas juntas. Variáveis de
ambiente definem os padrões do deployment; administradores podem sobrescrever o
provider e o modelo de conversa por organização no banco de dados. Nenhum seletor de
provider ou modelo é exposto no produto ou nas tools de configuração da
organização.

Depois da migration `228-org-voice-config`, escolha OpenAI para uma organização:

```sql
INSERT INTO organization_settings
  ("organizationId", voice_provider, voice_model, "createdAt", "updatedAt")
SELECT id, 'openai', 'gpt-live-1', now(), now()
FROM organization WHERE slug = '<org-slug>'
ON CONFLICT ("organizationId") DO UPDATE
SET voice_provider = EXCLUDED.voice_provider,
    voice_model = EXCLUDED.voice_model,
    "updatedAt" = now();
```

Defina `voice_provider = 'elevenlabs'` e `voice_model = NULL` para usar a
ElevenLabs com `ELEVENLABS_CONVERSATION_MODEL`. Um `voice_model` explícito da
ElevenLabs seleciona o LLM de conversa dela, não o modelo de síntese de fala.
`ELEVENLABS_VOICE_MODEL` e `ELEVENLABS_VOICE_ID` continuam controlando a síntese de
fala e a voz. Uma sobrescrita de modelo exige um provider explícito, para que mudar
o padrão do deployment não aplique o ID de modelo de um provider a outro.

Defina as duas colunas como `NULL` para restaurar os padrões do deployment. Mantenha
`voice_mode` ativado separadamente. Essas colunas não contêm credenciais; a chave do
provider selecionado precisa existir em toda réplica da API, e uma chave ausente
retorna um erro sem trocar de provider. Um `VOICE_CONVERSATION_PROVIDER` inválido
não impede a inicialização da API. Chamadas de voz que herdam esse padrão inválido
retornam 503; uma organização com uma sobrescrita de provider válida ainda pode usar
voz. O chat em texto comum não é afetado.

A leitura existente de organization-settings resolve as sobrescritas quando uma
chamada começa. Não há consulta adicional ao banco ou lookup por turno. O provider e
o modelo resolvidos ficam armazenados na reserva de sessão e permanecem fixos para
aquela chamada, mesmo que o banco mude antes do WebRTC conectar. Mudanças no banco
se aplicam à próxima chamada sem precisar de restart. Mudanças de ambiente ainda
exigem reiniciar toda réplica. A primeira chamada com uma nova configuração da
ElevenLabs pode provisionar um agent privado; chamadas seguintes o reutilizam. O
agent em execução e seu modelo não são afetados.

## Comportamento de sessão e limites

O navegador encerra sessões após dez minutos, com uma sessão ativa por usuário por
organização. A ElevenLabs também aplica esse limite no provider. Para a OpenAI, dez
minutos é um limite do navegador do Studio, não um limite de sessão aplicado pelo
provider. Até 40 pedidos de trabalho podem ser delegados em uma sessão. Um navegador
interrompido que não consegue liberar sua reserva pode precisar esperar essa
expiração antes de reconectar. O provider de voz selecionado cobra a conversa na
conta do deployment. A ElevenLabs usa Gemini 2.5 Flash por padrão para a conversa,
sem uma chave de modelo separada. A OpenAI usa seu modelo Live configurado para
conversa fala-para-fala. A contabilização de uso de modelo do Studio continua
cobrindo as chamadas de modelo do agent em execução.

Áudio de microfone e respostas em streaming trafegam diretamente entre o navegador
e o provider selecionado via WebRTC. A ElevenLabs usa transcrição Scribe e seu
modelo de síntese de fala configurado. O GPT-Live lida com escuta e fala simultâneas,
e emite fragmentos de transcrição e IDs de delegação. Seu adaptador envia a nova
fala como mensagem de chat pela mesma API de chat. Turnos falados anteriores viajam
ao lado como `voiceTranscript` e chegam ao agent em execução como contexto por
turno que o chat não exibe. Um evento de delegação é necessário; fragmentos de
transcrição sozinhos nunca iniciam trabalho. Uma janela curta de espera permite que
fragmentos atrasados cheguem, mas as transcrições do provider não têm um marcador de
turno concluído, então isso ainda precisa de avaliação com áudio real.
Client tools da ElevenLabs enviam pedidos, leem o status do chat atual e solicitam
cancelamento. O GPT-Live responde o status a partir do status de trabalho fornecido
e delega pedidos de cancelamento ao agent em execução, então esses pedidos podem
esperar atrás de trabalho ativo. O controle visível Stop agent work continua
disponível para cancelar a execução atual imediatamente. Nenhum dos dois providers
espera tarefas de código longas antes de continuar a conversa falada.
Resultados chegam pelo stream de chat existente do Studio e são fornecidos como
contexto para a companion. O navegador solicita um anúncio falado quando o usuário
está em silêncio. As verificações de permissão e aprovação permanecem no caminho
normal do Studio.

Pedidos delegados e respostas do agent permanecem no histórico normal do chat do
Studio. Comentários de conversa e perguntas de progresso ficam na sessão de voz.
Texto recente do chat e o contexto da página atual são fornecidos para a companion
quando a voz é iniciada. O Studio não armazena áudio. O agent provisionado na
ElevenLabs desativa a gravação de áudio e solicita retenção de transcrição de um
dia. Essas configurações da ElevenLabs não se aplicam à OpenAI; o tratamento de
dados da OpenAI segue a conta da OpenAI do deployment e seus controles de dados de
API.

Durante um deployment contínuo, navegadores mais antigos podem continuar usando os
endpoints originais de Scribe/TTS. Seus grants de fala assinados mantêm o limite de
dez minutos, 120 pedidos de síntese e um limite de 24.000 caracteres.

Sair do chat, trocar de organização ou desconectar encerra a sessão de voz. Falhas
de transporte mostram um erro com um caminho de volta para texto. Elas não
reenviam automaticamente um pedido cuja aceitação é incerta. Verifique o chat antes
de repeti-lo. Parar a reprodução deixa o trabalho do agent em execução.

## Verificação

A suíte regular de navegador `voice-mode.spec.ts` verifica os gates de acesso, a
flag padrão e a troca de volta para um rascunho preservado. Seu caso opcional ao
vivo exige um servidor de API configurado com um dos providers de voz e uma entrada
WAV sintética:

```bash
E2E_VOICE_LIVE=1 E2E_VOICE_WAV=/tmp/synthetic-utterance.wav \
  bun run --cwd=packages/e2e test:e2e -- tests/voice-mode.spec.ts
```

O caso ao vivo usa o serviço de fala real e um stand-in HTTP de modelo, e verifica
que a companion responde enquanto o modelo em execução está atrasado, anuncia seu
resultado e volta para texto no mesmo chat. Para a ElevenLabs, com
`E2E_VOICE_FOLLOWUP=1`, use um WAV contendo um pedido de trabalho seguido de uma
pergunta de progresso; o teste também verifica que a segunda resposta falada chega
antes do trabalho terminar, sem enviar outro turno de código. O GPT-Live também
responde a partir do status de trabalho fornecido, mas essa asserção opcional só foi
executada contra a ElevenLabs.

A suíte do daemon também exercita o executável real do Claude Code e o SDK contra um
stand-in HTTP de modelo. Ela começa em texto, muda um arquivo no modo de voz e volta
para texto verificando a mesma sessão do Claude e o histórico de conversa:

```bash
DAEMON_E2E_CLAUDE_VOICE=1 \
  bun test packages/sandbox/daemon-e2e/daemon.voice-claude.e2e.test.ts
```

Compile o daemon em Go primeiro, como descrito no README do pacote sandbox. Defina
`DAEMON_E2E_CMD` para usar um binário de daemon em outro caminho.
