Voice mode replaces the web chat's messages and composer with a speaking orb.
An adjacent page or site preview stays open. The selected agent, model, page
context, tools, permissions, and message queue remain the same for delegated work.
A realtime conversation, provided by ElevenLabs or OpenAI, handles speech while
the selected Studio agent performs that work in the background. You can keep talking, ask about
progress, or submit another request while a coding task runs.

Coding agents keep running Claude Code in their existing sandbox. Voice mode
does not change the chat's pinned runtime, checkout, preview, or Claude session.
The voice response style travels with each turn because Claude Code restores
the original system prompt when resuming a session. Text turns explicitly
restore normal response style. Decopilot chats use the same speech transport.

Choose **Start voice mode** beside the composer and allow microphone access.
**Back to chat** stops the microphone and playback. It preserves the chat and
any running work. **Stop agent work** is a separate control. Speaking while a
reply plays interrupts the audio. Complete work requests join the chat's normal
queue; pauses and greetings do not start coding turns. ElevenLabs can answer current-chat status locally; GPT-Live delegates fresh status questions to the working agent.
Approvals, questions, errors, and queued requests remain visible in voice mode.

The companion acknowledges accepted work without claiming it has finished. When
the Studio agent finishes, its final text part is sent back to the companion,
which announces the result during a quiet gap. A per-turn instruction asks the
working agent for a short, natural answer. Switching back to text restores normal
response style for subsequent messages.

## Organization conversations

Voice mode also works with the Super Agent. It can delegate questions about
connected services, analytics, and task management through the same tools and
permissions as text chat. For example, ask it to inspect analytics, start two
independent tasks, and then ask about their progress while discussing another topic.
The Super Agent must have access to the relevant integrations. GA4 can answer
analytics questions; fulfillment or order status requires a connected order system.

The ElevenLabs companion's status tool tracks requests in the current chat, not all task-board
items. Fresh status for independent tasks is another request to the Super Agent.
If the agent creates tasks 1, 2, and 3 during this call, their creation can be
announced from the chat result. Their later completion is not yet pushed into
voice automatically; ask the Super Agent for fresh status. Work in the current chat uses its existing queue, so a fresh lookup
can wait behind an active turn even while the voice conversation remains responsive.

## Shared conversation interface

Both browser adapters implement `publishUpdate`, microphone controls, volume,
and session close, and report requests through `onDelegate`. Updates distinguish
quiet context from spoken announcements and can carry a delegation ID. This lets
Studio deliver several tasks' progress or results independently and out of order.
OpenAI maps these to Live thinking/commentary appends; ElevenLabs maps them to
contextual updates and explicitly labeled background messages. Provider tool names
and event schemas stay inside the adapters.

The intended subscription scope is tasks started or explicitly discussed in this
call. An unrelated task finishing elsewhere should remain silent. The interface
can carry these updates, but the current producer observes the active chat only.
The remaining implementation gap is recording the relevant task IDs and filtering
the existing task-board push events to that set. Re-entering voice would also need
to restore the chosen task set. A task-creation turn finishing does not establish
that the created tasks finished.

## Deployment setup

Provider selection is server-only, with no provider or model picker in the product.
ElevenLabs remains the default. Set these variables on every API replica:

```bash
ELEVENLABS_API_KEY=<elevenlabs-api-key>
```

The key needs ElevenAgents read and write access (`convai_read`, `convai_write`),
plus Text to Speech and Speech to Text access for older browser sessions. Keep it
on the server. Studio creates a private ElevenLabs agent for its voice configuration
and reuses it across sessions. Browsers receive a conversation token and a signed
Studio session token; they never receive the API key.
The web app needs HTTPS for microphone access, except on localhost. No inbound
provider callback or manual agent provisioning is required. API replicas must
share the same Studio authentication secret and NATS service.

To use OpenAI instead, configure:

```bash
VOICE_CONVERSATION_PROVIDER=openai
OPENAI_LIVE_API_KEY=<openai-api-key>
```

The OpenAI adapter uses GPT-Live with client delegation and browser WebRTC.
Studio negotiates the SDP offer on its authenticated API using a single-use
session reservation. The browser receives an SDP answer, not an OpenAI credential. It does not require an ElevenLabs key. Keep the ElevenLabs key
during a rolling deployment if older browsers still use the transcription/synthesis
endpoints. The long-lived OpenAI key stays on the API server. Provider selection
never falls back silently to the other provider when credentials are missing.

Then enable **Settings → General → Voice mode** for the organization. The
`voice_mode` organization flag defaults off. It is separate from authentication:
only the owning user can start a voice session for a writable, hosted chat.
Native terminal chats and read-only chats do not offer this mode.

Optional variables:

| Variable | Default | Purpose |
| --- | --- | --- |
| `VOICE_CONVERSATION_PROVIDER` | `elevenlabs` | `elevenlabs` or `openai` |
| `OPENAI_LIVE_MODEL` | `gpt-live-1` | OpenAI Live model |
| `OPENAI_LIVE_VOICE` | `marin` | OpenAI Live voice |
| `ELEVENLABS_VOICE_MODEL` | `eleven_v4_turbo` | Speech synthesis model |
| `ELEVENLABS_VOICE_ID` | `JBFqnCBsd6RMkjVDRZzb` | ElevenLabs voice |
| `ELEVENLABS_CONVERSATION_MODEL` | `gemini-2.5-flash` | Conversational LLM model ID supported by ElevenLabs |

The conversational model is a deployment setting, with no model selector in the
product. Set the same value on every API replica and restart them to apply it to
new voice sessions. Changing the ElevenLabs model selects a separate provisioned agent;
existing voice sessions continue with their original model. It does not change
the selected coding agent or its model. Unset or blank values use the default.

## Session behavior and limits

The browser closes sessions after ten minutes, with one active session per
user per organization. ElevenLabs also enforces that limit at the provider. For
OpenAI, ten minutes is a Studio browser limit, not a provider-enforced session limit.
Up to 40 work requests can be delegated in one session. An interrupted browser that
cannot release its reservation may need to wait for that expiry before reconnecting.
The selected voice provider bills the conversation to the deployment's account.
ElevenLabs defaults to Gemini 2.5 Flash for conversation, with no separate model key.
OpenAI uses its configured Live model for speech-to-speech conversation.
Studio's model usage accounting continues to cover the working agent's model calls.

Microphone audio and streamed replies travel directly between the browser and
the selected provider over WebRTC. ElevenLabs uses Scribe transcription and its
configured speech synthesis model. GPT-Live handles simultaneous listening and
speaking, and emits transcript fragments and delegation IDs. Its adapter assembles
new spoken requests with earlier conversational context and submits them through
the same chat API. A delegation event is required; transcript fragments alone never
start work. A short settling window allows delayed fragments to arrive, but provider
transcripts have no completed-turn marker, so this needs evaluation with real audio.
ElevenLabs client tools submit requests, read current-chat status, and request cancellation.
GPT-Live delegates status and cancellation requests to the working agent, so those
requests can wait behind active work. The visible Stop agent work control remains
available to cancel the current run immediately. Neither provider waits for long
coding tasks before continuing the spoken conversation.
Results arrive through Studio's existing chat stream and are supplied to the
companion as context. The browser requests a spoken announcement when the user
is quiet. Permission and approval checks stay in the normal Studio path.

Delegated requests and agent answers remain in the normal Studio chat history.
Conversational remarks and progress questions stay in the voice session. Recent
chat text and the current page context are supplied to the companion when voice
starts. Studio does not store audio. The provisioned ElevenLabs agent disables
audio recording and requests one-day transcript retention. Those ElevenLabs
settings do not apply to OpenAI; OpenAI data handling follows the deployment's
OpenAI account and API data controls.

During a rolling deployment, older browsers can continue using the original
Scribe/TTS endpoints. Their signed speech grants retain the ten-minute limit,
120 synthesis requests, and 24,000-character allowance.

Leaving the chat, changing organizations, or disconnecting stops the voice
session. Transport failures show an error with a path back to text. They do not
automatically resend a request whose acceptance is uncertain. Check the chat
before repeating it. Stopping playback leaves the agent's work running.

## Verification

The regular `voice-mode.spec.ts` browser suite checks access gates, the default
flag, and switching back to a preserved draft. Its optional live case requires
an API server configured with either voice provider and a synthetic WAV input:

```bash
E2E_VOICE_LIVE=1 E2E_VOICE_WAV=/tmp/synthetic-utterance.wav \
  bun run --cwd=packages/e2e test:e2e -- tests/voice-mode.spec.ts
```

The live case uses the real speech service and an HTTP model stand-in, and
checks that the companion responds while the working model is delayed, announces
its result, and returns to text in the same chat. For ElevenLabs, with `E2E_VOICE_FOLLOWUP=1`, use
a WAV containing a work request followed by a progress question; the test also
checks that the second spoken answer arrives before work completes without
submitting another coding turn. GPT-Live delegates fresh status requests, so that
optional assertion is not a provider-parity check.

The daemon suite also exercises the real Claude Code executable and SDK against
an HTTP model stand-in. It starts in text, changes a file in voice mode, and
returns to text while checking the same Claude session and conversation history:

```bash
DAEMON_E2E_CLAUDE_VOICE=1 \
  bun test packages/sandbox/daemon-e2e/daemon.voice-claude.e2e.test.ts
```

Build the Go daemon first, as described in the sandbox package README. Set
`DAEMON_E2E_CMD` to use a daemon binary at another path.
