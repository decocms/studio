## How Studio is organized

Studio uses a small set of concepts that build on each other. Once you understand them, everything else follows naturally.

- **Organization** — your top-level workspace. Everything belongs to an org: members, connections, agents, projects, and logs.
- **Members** — the people in your organization, each with their own role and permissions.
- **Connection** — a tool or service you've plugged in (GitHub, Slack, a database, your own API). Credentials are stored once, securely, and shared across your team. See [Connections](/en/studio/connections).
- **Agent** — an AI configured for a specific task: a focused set of tools, clear instructions, and a narrow purpose. See [Agents](/en/studio/agents).
- **Project** — a shared workspace that brings agents and connections together around a goal or team. See [Projects](/en/studio/projects).
- **Virtual MCP** — a custom endpoint that composes tools from multiple connections into one. Agents and projects are both Virtual MCPs. See [Virtual MCPs](/en/studio/virtual-mcps).
- **Automation** — an agent run that happens on a schedule or when a specific event occurs. See [Automations](/en/studio/automations).
- **Thread** — a conversation session with an agent. Studio saves the history and tracks status so you can come back to ongoing work.
- **Store** — the built-in marketplace for discovering and installing tools and integrations. See [Store](/en/studio/store).
- **AI Provider** — a configured AI model (Anthropic, OpenRouter, Google, or the Deco AI Gateway) that powers your agents and chat. See [AI Providers](/en/studio/ai-providers).

## Agents vs. Projects

Both agents and projects are ways to work with tools in Studio. The difference is scope and purpose.

**Projects** are for ongoing work with a team:
- **Broad scope** — cover multiple workflows and capabilities within a work context
- **Long-lived** — evolve over time as work progresses
- **Team collaboration** — a shared workspace anyone on the team can use
- **Example** — a "Store Migration" project with inventory sync, order management, and customer data tools
- **When to use** — organizing work by product line, client, team, or initiative

**Agents** are focused tools for a specific job:
- **Narrow scope** — a clear, focused purpose with only the tools it needs
- **Task-specific** — designed for one type of operation or workflow
- **Clean slate each time** — each conversation starts fresh, without leftover context
- **Example** — a "Refund Processing" agent that only handles customer refunds and returns
- **When to use** — repetitive tasks, specialized workflows, or operations you want to standardize

Think of projects as your team's workspace and agents as the specialists you call in when you need a particular job done.

## How the protocol works

deco Studio is built on the [Model Context Protocol](https://modelcontextprotocol.io/) (MCP), an open standard for connecting AI clients to tools and services. You don't need to understand MCP to use Studio, but knowing the three building blocks helps:

- **Tools** — actions an AI can take (search a database, send an email, create a file)
- **Resources** — read-only data sources that give an AI context (documents, configs, org data)
- **Prompts** — reusable templates for common workflows, with variables you can fill in

Studio sits between your AI clients (like Claude Desktop or Cursor) and your tools, handling authentication, routing, and logging for every request.

## How a request flows through Studio

When an agent calls a tool, here's what happens:

```
┌─────────┐                    ┌──────────────┐                  ┌────────────┐
│ Client  │ ──[authenticate]──▶│  deco Studio │ ──[with creds]──▶│ MCP Server │
│ (Cursor)│                    │              │                  │  (GitHub)  │
└─────────┘ ◀──[response]──────└──────────────┘ ◀─[response]─────└────────────┘
                                      │
                                      └──▶ [audit log]
```

1. The client authenticates to Studio
2. Studio checks whether the client has permission to use the requested tool
3. Studio retrieves the stored credentials for that connection
4. Studio forwards the request to the upstream service
5. Studio logs the invocation — tool, timing, inputs, outputs, and who called it
6. Studio returns the response to the client

This means credentials never leave Studio, every action is logged, and access is consistent regardless of which client is making the request.

## Team access and permissions

Organizations provide the top-level boundary for everything in Studio. Connections, agents, projects, credentials, and logs are all org-scoped. This makes it easy to:

- Give different team members access to different tools
- Isolate work by client, department, or product line
- Track exactly who used what and when

---

## Why Studio uses composition

Instead of configuring complex integrations from scratch, Studio lets you build up from simple pieces:

**Connect** individual tools (GitHub, Slack, databases)

**Compose** them into agents or projects with a curated set of capabilities

**Share** through a single endpoint your team can use

This means you can add or remove tools without touching infrastructure, and non-developers can combine capabilities that would otherwise require custom code.

---

## Why monitoring is built in

Without a control plane, every client manages its own logs — or doesn't log at all. Studio logs every tool call that flows through the platform, creating a single place to debug failures, track costs, and audit who accessed what. There's no extra setup required.
