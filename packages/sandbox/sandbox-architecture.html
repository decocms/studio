    What moves

    Studio's call sites stay the same: it still calls a SandboxProvider. What changes is who holds the cluster credentials, how Studio reaches a daemon, and how a new image variant reaches a cluster.

    ConcernTodayTarget
    Cluster credentialsStudio's ServiceAccount: claims, routes, pods, pods/portforwardThe controller only. Studio has none. The data-plane agent can write sandbox.deco.cx objects and nothing else.
    Studio → daemonA port-forward through the apiserver on every call, production includedDirect to in-cluster Service DNS with the per-claim bearer
    Daemon config + tokenPosted by the provider inside the Studio processPosted by the controller before POST /sandboxes returns
    sandbox_runner_stateRead and written by the in-process providerOwned by the controller. Each row records runtime, image served and writer.
    Variant templatesRendered by a Helm helper from imageVariantsRendered by the controller from a SandboxVariant, copied from the live default template, and garbage-collected with it
    Variant resolutionStudio probes BASE-VARIANT[-medium] and logs when it falls backThe controller resolves it and returns the fallback as image.served
    Shipping a variantStudio PR, studio release, then a values PR in each environmentDockerfile PR in infra_applications. CI calls TAG_SET on decocms/control-plane, which writes a SandboxVariant to each cluster.
    Local dev sandboxNone since the desktop link was removedThe docker runtime, started by bun run dev
    Self-hostingChart plus the in-process providerChart plus the controller. The chart writes SandboxVariants, so nothing closed is needed.

    The open / closed line

    Anything a claim depends on is open source. Fleet management is closed. The two services never call each other: they meet in the cluster, through two contracts that live in the open repo.

    Open source

    decocms/studio
    • Studio API: handles, tools, dispatch, preview edge, credential minting, RemoteSandboxProvider
    • Sandbox controller (Go): claims, SandboxVariant reconciliation, variant resolution, daemon config and token, lifecycle, agent-sandbox and docker runtimes
    • Daemon, base image, daemon-go/pkg/protocol
    • @decocms/sandbox-controller-types: TypeScript types generated from the Go ones, which the control plane renders against
    • sandbox-env chart: default template and pools, imageVariants written as SandboxVariants, gateway, housekeeper
    Contracts
    Controller HTTP APIStudio speaks it · the controller implements it
    SandboxVariant CRDthe chart, kubectl and the control plane write it · the controller reconciles it

    Closed · deco only

    decocms/control-plane · decocms/operator · decocms/infra_applications · no new repo
    • Variants feature in the existing control plane: desired variants per cluster, prewarming, SANDBOX_VARIANT_* tools, a console tab
    • Data-plane agent (from decocms/operator), installed on the sandbox cluster for the sandbox.deco.cx group only
    • Variant images: Dockerfiles, smoke.sh, a CI that builds FROM each base tag
    • Later: per-org tenant pools, cross-cluster views, audit trail

    Test for the line: a self-hoster running Studio, the chart and the controller gets working sandboxes, variants included. On deco's clusters, a control-plane outage freezes the catalog but never blocks a claim.

    Three phases, low risk first

    The controller reaches production doing a job that can't break a sandbox start: reconciling variants. It takes claims last.

    Phase 1 · controller, variants only

    Open source. Studio keeps its in-process runner.

    1. #7461 · #7469 per-repository image, string schema, chart imageVariants, Flutter removed from the base image
    2. controller-go, variants only, under its final module path
    3. SandboxVariant CRD and reconciler with an image check, owner references and status
    4. Controller chart and image, claim API off, variant permissions only
    5. Types package @decocms/sandbox-controller-types, generated from Go
    6. Chart N marks variant templates keep. Chart N+1 writes SandboxVariants and the controller adopts the templates.
    7. Detection on link and the sandbox-base-released dispatch

    Phase 2 · deco variants via control plane

    Closed. 2–3 days on top of what hosting already runs.

    1. infra_applications Dockerfile, smoke.sh and CI
    2. Agent install on the sandbox cluster, group sandbox.deco.cx, dry-run first
    3. Variants feature in decocms/control-plane
    4. Handover per environment: set keep on the variant, run ADOPT android, then set imageVariants to empty
    5. Delete image-android/ and its release job

    Phase 3 · controller takes claims

    Open source. This is the risky part.

    1. Claim path in: #6187 ported against main, pkg/protocol, RemoteSandboxProvider behind a default-off flag
    2. docker runtime, so bun run dev has a sandbox again
    3. Tenant pools in Go. Until this lands, prod can't cut over.
    4. Claim API on in staging, with GET /images and a capacity check per variant's nodes
    5. Drained prod cutover. The same PR deletes the in-process runner, client-node and Studio's Role.
    Two implementations exist until the cutover lands. Don't leave it half done.

    Traps on the way

    Things that are easy to miss in review and expensive to find in production.

    Handover
    Helm deletes what you hand over

    The templates are owned by their SandboxVariant, so if Helm deletes that object, Kubernetes deletes the templates too. Mark it keep and let the agent adopt it before dropping it from deco's values.

    Cutover
    A rolling deploy makes token rotation ping-pong

    An old pod rehydrates a claim the controller owns and rotates its token, and the controller rotates it back, over and over. Record the writer on each row, and cut over by draining.

    Parity
    Tenant pools are ignored in Go

    STUDIO_SANDBOX_TENANT_POOLS does nothing in the Go runtime today. Cutting over prod without the port breaks those pools without any error.

    Server-side apply
    Dropping force breaks previews

    Without LEGACY_SSA_FIELD_MANAGER and force: true, the first apply after cutover fails with a 409. The route has no backend, and the browser reports the empty 500 as a CORS error.

    Capacity
    Check capacity on the variant's nodes

    With the KVM nodes full and every other node idle, an android claim can't be scheduled. A fleet-wide capacity check would still report room.

    Go module
    Rename the module before anyone imports it

    github.com/decocms/studio/sandbox-controller can't be imported from outside the repo. A closed runtime would need …/packages/sandbox/controller-go and tagged releases.
